理解 Matmul 的分块，不能只看 `baseM`、`baseN`、`baseK` 三个数。完整的计算还要回答：每个核负责 C 的哪一块，A 和 B 怎样从 GM 搬进 L1，L1 中的数据怎样送到 L0，以及 K 方向的部分结果在哪里累加。

这篇笔记整理自 2026 年 10 月 8 日的手绘图，沿着“任务划分 → 分层搬运 → 基础计算 → 结果写回”展开。文中的容量都是用于推算的假设，示意伪代码没有经过设备运行验证。

## 1. 三种块分别解决三个问题

从矩阵乘开始：

```text
A [M, K] × B [K, N] = C [M, N]
```

| 层次 | 关注的范围 | 要解决的问题 |
| --- | --- | --- |
| 单核任务 | singleCoreM × singleCoreN 的输出区域 | 谁负责算哪部分 C |
| L1 窗口 | A、B 在当前阶段驻留 L1 的数据 | 一次准备多少输入，怎样复用 |
| L0 基础块 | A 的 baseM × baseK、B 的 baseK × baseN、C 的 baseM × baseN | 一次基础计算使用哪些数据 |

单核任务可以包含很多输出基础块。L1 窗口也可以覆盖多个基础块，让已经搬入的数据被多次计算使用。`singleCore` 和 `base` 对应不同层次；官方 Matmul 实现说明也分别描述了单核 Shape 与基础分块。[Matmul 算子实现说明](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/programug/Ascendcopdevg/atlas_ascendc_10_0038.html)

原图上方还对比了“标准 Tiling”和“示例中的 Tiling”。这里更适合将它们理解成两种示意：一种显式区分单核块与基础块，另一种把这两个层次简化或合并。原笔记没有给出所指 `cann-samples` 示例的文件路径和提交版本，因此不能据此断言整个示例项目都没有进行单核划分。

## 2. 多核划分是任务分配，不一定是一个串行循环

原图第一层把 C 划成多个绿色区域，每块作为一个单核任务。可以沿 M、沿 N，或者同时沿 M 和 N 划分，具体取决于矩阵形状、可用核数与数据复用方式，并非必须两个方向都切。

如果任务块大小为 `singleCoreM × singleCoreN`，需要覆盖的逻辑块数为：

```text
任务块数 = ceil(M / singleCoreM) × ceil(N / singleCoreN)
```

这些任务应映射到可用核上。任务块多于同时工作的核数时，一个核也可能继续处理其他任务块。因此，图中的“第一层循环”可以理解为遍历任务空间，不代表所有绿色块都由同一个核串行执行。

后续沿用原图假设：一个核当前负责 `1024 × 1024` 的输出区域，K 长度为 1000，不在核间拆分 K。

## 3. GM → L1：算出能够驻留的 K 窗口

假设 A、B 都是 float16，每元素 2 字节，L1 可用容量为 256 KiB，暂不考虑双缓冲和其他开销。为了对应原图，让 A 窗口覆盖本核全部 1024 行，B 窗口覆盖本核全部 1024 列。

设这一阶段装入的 K 长度为 `K_L1`：

```text
A 窗口形状 = [1024, K_L1]
B 窗口形状 = [K_L1, 1024]

A、B 总字节数 = (1024 × K_L1 + K_L1 × 1024) × 2
             = 4096 × K_L1
```

容量约束给出：

```text
4096 × K_L1 ≤ 256 × 1024
K_L1 ≤ 64
```

取 `K_L1 = 64`，A 和 B 各占 128 KiB，总计恰好 256 KiB。原图“平分 L1”的计算在这组对称尺寸下成立，但不是通用的分配规则。

这里的 64 是**该容量模型下的上界**：它已经用满假设的空间。若 A、B 的整个窗口都做双缓冲，且其他条件不变，需求会翻倍；在相同的理想容量模型下，K 窗口上界随之降为 32。实际还要检查对齐、数据布局、额外占用和平台约束。

### K=1000 时最后一轮处理多少数据

```text
ceil(1000 / 64) = 16 轮
前 15 轮覆盖 960 个 K 元素
最后 1 轮剩余 40 个有效元素
```

最后一轮不能无条件按 64 个有效元素读取。需要按使用的 API 和数据格式处理尾块，例如补零或使用相应的尾块参数，同时保证 GM 访问不越界。

## 4. L1 → L0：容量上界不等于实际 baseK

原图继续假设 L0A、L0B 各有 64 KiB，并取：

```text
baseM = 64
baseN = 64
```

只从 L0A 的单份输入容量推算：

```text
64 × baseK × 2 ≤ 64 × 1024
baseK ≤ 512
```

L0B 得到相同的容量上界。**这只能说明 512 是单独按容量算出的上限，不能推出本例必须或能够采用 baseK=512。**

原因在于，前面的 L1 窗口当前只准备了 64 个 K 元素。在本文采用的“从当前 L1 窗口取数据完成一次基础计算”的路径下，不能把尚未准备好的 512 个 K 元素当作已经就绪。若要跨多个 L1 窗口拼装更大的 L0 块，需要另行设计装载、累积填充与同步流程，原图没有展开这种方案。

为了得到一组连贯的示例，下面选择 `baseK = 64`：

| 缓冲 | 数据块 | 容量计算 | 占用 |
| --- | --- | --- | --- |
| L0A | 64 × 64 的 float16 | 64 × 64 × 2 | 8 KiB |
| L0B | 64 × 64 的 float16 | 64 × 64 × 2 | 8 KiB |
| L0C | 64 × 64 的 float 累加块 | 64 × 64 × 4 | 16 KiB |

未用满 L0A / L0B 并不矛盾：参数必须同时服从数据准备、容量、格式、对齐和调度条件。本节使用 `≤` 进行理想容量估算；原图写出的严格不等式，以及具体接口对缓冲倍数、边界值的限制，仍需按目标平台检查，不能把“刚好装满”当作已验证配置。

## 5. K 循环放在哪里，决定了部分结果存在哪里

原图按“单核任务 → K 分段 → 输出基础块”的顺序解释三层循环。这个顺序能突出输入复用，但还缺少一个关键条件：切换输出基础块时，之前的部分和如何保留？

本核 `1024 × 1024` 的输出，按 float 累加需要：

```text
1024 × 1024 × 4 = 4 MiB
```

它包含 `16 × 16 = 256` 个 `64 × 64` 输出基础块。如果先对第一个 K 窗口遍历全部 256 个输出块，就必须保存这 256 份部分结果，才能在第二个 K 窗口继续累加。不能默认它们都一直留在 L0C。

因此，完整实现必须说明累加策略。例如，固定少量输出块，遍历 K 完成它们；或者把部分和存到其他合适的位置，后续再读回累加。不同方案影响输入复用、搬运量和所需空间。

### 一个便于理解的循环顺序

下面采用“固定一个输出基础块，做完全部 K，再写回”的教学模型。它不追求最优的 L1 复用，并且省略搬运同步、尾块处理及 API 细节：

```text
各核处理分配给自己的 singleCore 任务：
    遍历本任务的每个 64×64 输出块：
        初始化该块的 L0C 累加结果

        遍历 K 方向的 16 个窗口：
            准备该输出块所需的 A、B 输入片段到 L1
            从 L1 搬运当前基础输入块到 L0A / L0B
            执行矩阵乘，并累加到同一个 L0C 输出块
            最后一个窗口只含 40 个有效 K 元素

        写回这个输出块的最终结果
```

这里不要求一直保留前面完整的 `1024×64` 和 `64×1024` 宽窗口；可以按当前输出块缩小实际搬入范围。为了保持教学模型连贯，K 步长仍取 64。若重新选择窗口尺寸与循环顺序，就应重新计算容量和复用收益。

更高效的实现可能一次处理一组输出块，使 A、B 在它们之间复用。关键是先说明这组输出块的部分和如何保存，再决定 K 与 M/N 小块循环的嵌套关系。

## 6. L0C → GM：区分最终结果与部分结果

原图最后强调“完成所有 K 轴元素的计算后，才能搬运 L0C”。对于上面的教学模型，更准确的表述是：**当前输出块完成全部 K 归约后，才把它作为最终 C 写回。**不需要等整个单核的所有输出块都计算结束。

若采用分段累加、部分和落盘或其他归约方案，中间结果也可能提前搬出，但后续必须继续正确合并；它们不能直接被当成最终输出。实际从 L0C 输出采用什么指令或接口，由芯片及 Matmul 实现决定。高阶 API 中也区分计算迭代与结果获取，应按相应接口约定使用。[Iterate 与结果获取说明](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/850/API/ascendcopapi/atlasascendc_api_07_0638.html)

## 7. 用同一组假设检查整条链路

回看原图时，可以按下面的顺序核对：

1. 明确一个核负责的 M/N 范围，以及 K 是否需要跨核归约。
2. 用实际驻留的 A、B 窗口和缓冲份数计算 L1 占用。
3. 同时检查 L0 容量与输入就绪范围，避免仅从 L0 倒推出 baseK。
4. 处理 K 尾块，明确有效长度与对齐后的存储长度。
5. 写出循环顺序，并标出每份部分和的存放位置与存活时间。
6. 确认写回的是最终结果，还是后续仍要累加的中间结果。

原图串起了 Matmul 的主要数据路径；把容量推算和累加生命周期补齐后，它才能进一步指导具体实现。关于 L1 窗口及缓冲份数，可以接着阅读[从多核划分到 L1 双缓冲](/posts/ascend-c-matmul-tiling/)；关于搬运与计算之间的依赖，可参考[SetFlag / WaitFlag 流水同步笔记](/posts/ascend-c-pipeline-sync/)。
